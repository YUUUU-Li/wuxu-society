# 提交规范（Conventional Commits）

> 适用范围：本仓库 `YUUUU-Li/wuxu-society` 的所有人工提交（编委、维护者、Agent 均同）。
> 依据：[Conventional Commits 1.0.0](https://www.conventionalcommits.org/zh-hans/v1.0.0/)。
> 生效时间：**2026-11-01 起**。历史提交不追溯重写；新旧混杂时，以本规范之后的提交为准。

## 一、三条总则

1. **一次提交只做一件事**：一个功能、一个修复、一组同主题文档。不要把"改作品 + 调样式 + 升依赖"塞进同一条。
2. **提交前 `npm test` 必须全绿**；只提交本次改动涉及的文件（`git status` 逐项确认），不提交 `dist/`、`node_modules/`、构建期生成的 `src/static/LICENSE*.txt`。
3. **不逐次 push**：本地可以多次提交，按里程碑或用户要求批量推送；推送命令照《编委操作手册》§4（带代理）。

## 二、基本格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

- 第一行是**标题**：`type(scope): subject`；
- 标题与正文、正文与页脚之间**各空一行**；
- 标题**不超过 50 个字符**（含类型与范围），**句末不加句号**；
- `type`、`scope` 用小写英文；`subject` 用中文（本仓库惯例）；
- 正文写"做了什么、为什么"，不写"怎么改的"（代码本身说明怎么改）；可分行、可用 `-` 列表；
- 页脚写破坏性变更、关联 issue/PR（可选）。

命令示例（正文用第二个 `-m`）：

```bash
git -c core.autocrlf=false commit -m "fix(library): 后退返回作品库时按 URL 重新筛选" -m "浏览器恢复下拉框但不触发 change，列表仍是全量；改为以 URL 为准重算，并监听 pageshow。"
```

**可选：启用仓库自带的提交模板**（`git commit` 不带 `-m` 时会自动带出提示，注释行不会进提交信息）：

```bash
git config commit.template .gitmessage
```

## 三、type（必填，取其一）

| type | 用途 | 本站例子 |
|---|---|---|
| `feat` | 新功能、新页面、新能力 | `feat(submit): 投稿页新增创作时间选择` |
| `fix` | 修复 bug | `fix(library): 修复筛选后返回列表错位` |
| `docs` | 只改文档（含 README、docs、注释性说明） | `docs(commit): 新增提交规范` |
| `style` | 不影响行为的格式/样式调整（缩进、空格、CSS 纯视觉微调） | `style(nav): 调整手机端导航间距` |
| `refactor` | 重构：不改外部行为，也不修 bug | `refactor(scripts): 名单改由作品目录推导` |
| `perf` | 性能优化 | `perf(stats): 给回溯查询补路径索引` |
| `test` | 只增改测试 | `test(stats): 补有效阅读门槛断言` |
| `build` | 构建系统、依赖、打包配置 | `build(deps): 升级 Eleventy 到 2.0.1` |
| `ci` | CI / 自动部署配置 | `ci(deploy): 调整 Cloudflare 构建命令` |
| `chore` | 杂项：数据回填、脚本工具、非源码维护 | `chore(data): 补填 8 篇创作时间` |
| `revert` | 回滚某次提交 | `revert: feat(submit): 投稿页新增创作时间选择` |

> `docs` 与 `chore` 的边界：**文档正文用 `docs`**；**数据/工具/配置类维护用 `chore`**（如批量补 `created`、改词表 seed、更新生成物）。

## 四、scope（建议填写，取本站模块名）

scope 说明"改动落在哪一块"，用下表的小写英文；**一次只写一个**，确实横跨多处时取最主要的一块，或省略。

| scope | 对应位置 |
|---|---|
| `works` | `src/works/*.md` 作品正文与 front matter |
| `issues` | `src/_data/issues.json`、封期脚本、期页 |
| `concepts` | `src/_data/concepts.json`、概念页 |
| `tags` | 标签大纲、`functions/api/tags.js`、标签 SQL |
| `comments` | `functions/api/comments.js`、评论/回帖前端 |
| `auth` | `functions/api/auth.js`、登录注册、账号 |
| `submit` | `functions/api/submit.js`、`src/submit.njk` 投稿 |
| `join` | `functions/api/join.js`、入社申请与名册草稿 |
| `preview` | `functions/api/preview.js`、投稿预览 |
| `stats` | `functions/_middleware.js`、`stats.js`、`hit.js`、`beacon.js` |
| `library` | `src/library.njk`、作品库筛选/排序 |
| `members` | `src/_data/members.json`、`src/members.njk` |
| `yaji` | `src/yaji.njk` 雅集页 |
| `ui` | 全站布局、导航、页脚、主题、交互（`src/_includes/`、`site.css`、`site.js`） |
| `scripts` | `scripts/` 下的构建/维护工具 |
| `data` | 数据回填与迁移（`created`、词表 seed 等） |
| `docs` | `README.md`、`docs/`、`PROJECT-NOTES.md` |
| `commit` | `docs/提交规范.md`、`.gitmessage` 等提交约定 |
| `deploy` | 托管、域名、环境变量、部署配置 |
| `deps` | 依赖与锁文件 |

> 历史提交里出现过 `fix(投稿流程)`、`chore(数据)` 这类中文 scope；**新提交一律使用上表英文 scope**，同一模块不要两种写法混用。

## 五、subject（必填）

- 用**陈述句**写"这条提交做成了什么"，而不是"我在改什么"；
- 中文，句末不加句号；不用"更新""修改一下""若干"这类无信息量的词；
- 首字母/首个汉字直接进入动作，不加"我"；
- 同一个词的写法保持一致（如统一用"作品库"而不是"库页""列表页"混用）。

## 六、body（建议填写）

适合写：

- **为什么**要改（现象、触发条件、根因）；
- **影响范围**（哪些页面/接口/数据）；
- 口径或兼容性说明（如"旧链接自动 301"）；
- 已知限制或后续待办。

不适合写：

- 逐行解释代码（diff 已经说明）；
- "按用户要求""修复了一些问题"这类空话；
- 与本次改动无关的内容。

## 七、footer（按需）

### 关联 issue / PR

```
Closes #12
Refs #34
```

### 破坏性变更（Breaking Change）

标题加 `!`，或在页脚写 `BREAKING CHANGE:`：

```
feat(api)!: 投稿接口改为返回 slug 字段

BREAKING CHANGE: 旧客户端读取的 file 字段已移除，请改读 slug。
```

本站常见的破坏性变更：作品 URL/文件名规则改变、接口字段增删、数据字段迁移（如 `created` 口径）、函数路由变更。**这类改动必须在正文说明迁移方式。**

### 回滚

```
revert: feat(submit): 投稿页新增创作时间选择

This reverts commit 1a2b3c4d.
```

## 八、示例

### 好的提交

```
feat(submit): 投稿页新增创作时间选择

投稿可以选择到年/月，日可选；日期同时决定作品排序与归辑。
后端按同一口径归一化为 YYYY[-MM[-DD]]。
```

```
fix(library): 后退返回作品库时按 URL 重新筛选

Chrome/Edge 在 bfcache 未命中时会重载页面，浏览器恢复下拉框但不触发
change，列表仍显示全量。改为以 URL 为准重算，并监听 pageshow。

Closes #12
```

```
docs(docs): 校正作品数与已删除登记表的说明

README 的作品数应与 src/works 保持同步；自定义指南的自查清单不再要求已删除的共享登记表。
```

```
chore(data): 补填 8 篇创作时间
```

### 应避免的提交

| 反例 | 问题 |
|---|---|
| `update` / `修改` / `fix bug` | 没有类型、范围与信息量 |
| `feat: 改了很多东西` | 一次提交混多个主题 |
| `fix(library): 修复筛选问题。` | 句末多余句号，且"问题"未说明现象 |
| `feat(作品库): ...` | scope 用了中文，与规范表不一致 |
| 把 `dist/`、`node_modules/` 一起提交 | 产物/依赖不应入库 |

## 九、自动生成的提交与 PR（例外）

以下由系统生成，**不受本规范约束**，也不要手工改写：

- 投稿 PR 标题：`投稿：<题名>（<署名>）`；
- 入社 PR 标题：`入社申请：<昵称>`、名册草稿提交 `入社: 名册草稿 <昵称>`；
- GitHub 合并提交：`Merge pull request #N from ...`。

编委手工合并时若选择 **Squash and merge**，请把标题改成规范格式：

```
feat(works): 收录《题名》（署名）
```

## 十、提交前自查（30 秒）

- [ ] `npm test` 全绿；
- [ ] `git status` 只含本次要提交的文件；
- [ ] 没有 token、密钥、`.env`、个人隐私信息；
- [ ] 标题符合 `<type>(<scope>): <subject>`，≤ 50 字、无句号；
- [ ] 一次提交只做一件事；
- [ ] 破坏性变更已在标题加 `!` 或页脚写 `BREAKING CHANGE:`；
- [ ] 本次不打算逐条推送（按里程碑批量 push）。

> 维护口诀：**先测后提，一事一提交；类型定性质，范围定位置，标题说结果。**
