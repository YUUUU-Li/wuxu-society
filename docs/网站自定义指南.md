## 0. 全局概念：这个站是怎么拼出来的

```
md / json 内容  +  njk 模板(骨架)  +  site.css(皮)  +  site.js(动作)
        └────────── Eleventy 构建(npm run build) ──────────┘
                           └→  dist/ (纯静态 HTML)
                               └→ 推 GitHub main → Cloudflare Pages 自动发布(1-2 分钟)
```

- **改文字/内容**：多数情况只动 `src/works/*.md` 或 `src/_data/*.json`；
- **改布局/文案结构**：动 `src/*.njk`（页面级模板）与 `src/_includes/`（公共骨架）；
- **改样式**：`src/static/site.css`（唯一样式文件，内部有中文区块注释，可用 Ctrl+F 搜标题）；
- **改交互**：`src/static/site.js`（主交互；另有 `auth.js` 账号、`zhuzhu.js` 众注、`beacon.js` 有效阅读）；
- **改构建规则**：`.eleventy.js`；
- **改投稿后端**：`functions/api/submit.js`（入社申请为 `functions/api/join.js`）。

改完验证：`npm run build`（输出 `Wrote N files` 即成功）→ git 提交推送 → 等 1–2 分钟线上生效。

## 2. 作品内容（最常改的地方）

每个作品 = `src/works/<文件名>.md` 一个文件。**文件名就是网页地址**（如 `w-feng.md` → `/w-feng.html`），
改名永远安全（站内全部自动引用文件名），不要用中文/大写文件名。

### front matter（文件头 `---` 之间）可用字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `title` | ✅ | 题名 |
| `author` | ✅ | 署名，如 `zk（道格）`——`（笔名）`会被自动拆成"缩写 + 笔名" |
| `genre` | ✅ | 体裁（决定正文排版 + 筛选项） |
| `imageries` | | 意象标签数组，如 `["雨", "清明"]`（须是《标签大纲》里的词；用于作品库"意象"筛选与作品元信息） |
| `source` | | 出处/雅集，如 `清明雅集`（决定"同时同源"关联 + 筛选项） |
| `related` | | **唱和/组诗**等强关联：填对方文件名数组（可多篇） |
| `excerpt` | | 摘句（首页卡片缩略显示）；**留空自动取正文首句** |
| `epigraph` | | **题记**：楷体排在作品开篇（正文之前），可含 `\n` 换行 |
| `selfNote` | | **自注**：楷体排在正文下方（与正文隔一条细线），可含 `\n` 换行 |
| `fgenre` | | 列表/归档用的补充体裁说明（可选） |

> 其余字段（layout/permalink 等）已由 `src/works/works.11tydata.js` 自动生成，**不要手工写**。

### 正文里可用哪些"块"

正文是 HTML 片段，每段一个 `<p>`，段落种类（class）：

| 写法 | 效果 |
|---|---|
| `<p class="stanza">第一句<br />第二句</p>` | 诗句：行间自动断行 |
| `<p class="stanza kaiti">…</p>` | 楷体大段（自序/序文常用，见《芙蓉王诗》） |
| `<p class="prose">…</p>` | 散文段落 |
| `<p class="analysis">…</p>` | 赏析/评注块（自带分隔线样式） |
| `<p class="byline">…</p>` | 落款 |
| `<hr class="lib-hr" />` | 分隔线（长文分节用，见《文艺b与地雷女》） |

> 想换某篇的首页摘句：在 front matter 加 `excerpt: "你想要的句子"` 即可（不用改正文）。

## 3. 作品怎么"进各列表"

**只要把 md 放进 `src/works/` 就够了**——名单全部在构建期推导（见 `scripts/works-registry.js`）：

| 名单 | 来源 |
|---|---|
| 全站篇目（作品库平铺、全文源库、关联排序基准） | `src/works/` 下的所有 `.md` |
| 已入期 / 期页目录 | `src/_data/issues.json` 各期的 `slugs` |
| 其余社员作品（散作） | 全站篇目 − 已入期 |
| 待辑（雅集页"N 篇待辑"提示） | 作品 front matter 写了 `pending: true` 的（封期脚本会清掉） |

> **为什么不再用登记表**（2026-09 改）：`groups.json` / `fulltext_order.json` / `pending_issue.json` 这三份共享 JSON 已**删除**。
> 它们原由投稿函数各追加一行，导致两个投稿 PR 都改同一数组末尾——合并第一个后，第二个 PR 必然冲突（GitHub 报 "This branch has conflicts that must be resolved"）。
> 现在投稿 PR **只新增一个作品文件**，多个 PR 可以任意顺序依次合并。

| 文件 | 作用 |
|---|---|
| `concepts.json` | 概念档案：`{id, name, note(题解,可留空), related:[id]}`；某期 `issues.json` 的 `concepts` 填概念 id 后，自动生成概念页 `/concepts/<id>.html`，作品页与期页出现"本期概念"入口（id 用拼音/英文） |
| `issues.json` | 各期：`{id, title, type, period, epigraph, slugs:[…], concepts:[…]}`，由编委封期时写入（`npm run seal-issue`） |

## 3.5 作品排序与创作时间（`created`）

作品 front matter 的 `created` **写法很宽松**，认得出就统一归一化：

| 写法 | 归一化 | 含义 |
|---|---|---|
| `20240911` · `2024.9.11` · `2024/9/11` · `2024年9月11日` · `2024-09-11` | `2024-09-11` | 到日 |
| `202409` · `2024.9` · `2024年9月` · `2024-09` | `2024-09` | 只到月（**模糊**） |
| `2024` | `2024` | 只到年（**最模糊**） |
| 认不出的（`2024-13`、`去年春天`…） | 原样保留 | 按「**年份待考**」处理，并在构建日志里告警 |

- **排序**：**作品库全站平铺**、雅集页刊期档案、全文库页、关联作品组内，一律按 `created` **升序**（旧→新），且**模糊的往前排**（只到年的排在该年各月之前，只到月的排在当月有具体日子的之前：`2024` < `2024.6` < `2024.6.7`）。实现上把年月日补零成 8 位数字当排序键（`2024` → `20240000`、`2024-06` → `20240600`、`2024-06-07` → `20240607`）。口径的单一真相在 `scripts/work-order.js`（`.eleventy.js` 与 `scripts/work-dates-report.js` 共用，改动请改这一处并跑 `npm test`；口径单测 `scripts/test-dates.js`，会把投稿接口与投稿页的解析一起比对）；
- **展示**：作品详情页题下信息显示「创作时间 2024年3月6日」（归一化在 `src/works/works.11tydata.js` 的 `eleventyComputed.created`；`created` 为空则整条不显示）；
- **未填者**：**不猜日期**——一律排在已填者之后（组内按文件名次序稳定排列），作品库底部另立「**年份待考**」一节并标出篇数（筛选把该节筛空时，标题会自己收起）；
- **补填工具**：`npm run set-created -- <slug> <日期> [...]`（支持 `--dry-run`，日期同样接受上面那些宽松写法）；缺哪些、属哪一批、有什么线索，看 `docs/作品时间收集表.md`（重跑 `node scripts/work-dates-report.js` 刷新）；
- **投稿页**：年、月是下拉，「日」那一格是文本框——除 1–31 外还能**直接粘整串日期**（`20240911`、`2024.6.7`、`2024年6月7日`，或只到月的 `2024.6`），页面自动拆到年、月里并在下面回显「已识别：…」；投稿接口（`functions/api/submit.js`）也按同一口径校验与归一化；
- **改名**：`npm run rename-work -- <旧slug> <新slug>` —— 文件名、`issues.json` 期册、related 指向、名册链接、以及 `src/static/_redirects` 的 301 跳转一次改全（改完 `npm test` + 推送即可）；
- **归辑**：仍由编委人工封期（`npm run seal-issue`），创作时间用于期页/库内排序与封期时筛选参考；
- **排序基准**：展示顺序完全由 `created` 推导（不再是手工名单）；同一时点或未填时间者按文件名稳定排列。

## 3.6 浏览量统计（到达 / 有效阅读 / 读者，**只给编委看**）

2026-09 上线；**2026-10-13 改版：按"内容页 / 入口页"分开 + 真人/疑机分开**（起因：全站 247 个"访客"里 186 个只打了首页、225 个只看一页就走 —— 那是爬虫与预览抓取，不是读者）；**2026-10-30 再加一层"有效阅读"**：`src/static/beacon.js` 报停留/滚动/交互，**服务端复算够门槛**才算"真的读了"（见下面「有效阅读层」）。

**三个词别混**：**到达**（服务端看到一次打开的页面，不依赖 JS，是分母/上界）→ **有效阅读**（够门槛的"真的读了"，依赖 JS，是下界）→ **读者**（有效阅读里跨天去重的人，**只有它能回答"多少人"**）。

**站上不给读者显示任何数字**：作品页题下那块 `#work-stats` 默认 `hidden`，只有**编委登录后**（账号 `role='编委'`，或过渡期的旧钥匙）才由 `src/static/auth.js` 去 `/api/stats` 取数填入。

| 环节 | 文件 | 说明 |
|---|---|---|
| 计数（写） | `functions/_middleware.js` | 根中间件，官方支持"对整站生效、**包括静态文件**"；页面响应照常返回，计数用 `context.waitUntil` 异步写库，不拖慢访问 |
| 读取（读） | `functions/api/stats.js` | `GET /api/stats?work=<标识名>[&days=7][&diagnose=1][&derived=1][&csv=1][&key=<旧钥匙>]`；**仅编委**，未登录/读者一律 403 |
| 有效阅读（读+写） | `functions/api/hit.js` + `src/static/beacon.js` | beacon 用 `sendBeacon` 发 `POST /api/hit`，**服务端复算**门槛后写 `reads`；被拒一律 204，但原因记进 `hit_reject` |
| 建表 | `sql/stats.sql` | 幂等；**中间件与读取接口都会调同一个 `ensureStatsSchema()` 建表/给老库补列**（`functions/api/stats.js` 直接 import 中间件的那份，避免两处走样）。接口**自己会补表**是必须的：否则"刚部署完、还没有页面访问触发中间件"时，接口去查还不存在的列就会 500、界面一片空白（2026-10-13 线上真出过） |
| 展示 | `src/_includes/layouts/work.njk` + `src/static/site.css` + `src/static/auth.js` | 作品页题下一行小字：「本篇有效阅读 N · 读者 M【疑机 x】· 仅编委可见」——**主数字只报这一种**；“页面打开”（到达）只写进 `title` 作分母/诊断；首页 Hero 那行同理（全站口径） |

**三个桶（优先级从高到低）**：

| 桶 | 判定 | 列 | 含义 |
|---|---|---|---|
| `s` 疑机 | UA 命中爬虫/脚本/自动化工具黑名单、没有 UA、没有 `Accept-Language`，或来自机房 ASN 且没有 Sec-Fetch | `sviews/suniq` | 明确的机器人/脚本 |
| `c` 内容页（**到达层主口径**） | 不像机器，且路径是**内容页**：`/w-*`、`/qingming-*`、`/issue-*`、`/concepts/*`、`/_fulltext` | `views/uniq` | 服务端看到的"内容页打开/人次"；**只作分母，界面主数字不再报它** |
| `e` 入口页 | 不像机器，但是首页/作品库/社员/雅集/投稿/404 等"路过页" | `eviews/euniq` | 爬虫、链接预览、只瞄一眼就走 —— **不算进内容页数字**，但如实显示为"仅入口 N" |

**口径细节**（改动前先想清楚，旧数据不可重算）：
- **阅读 views** = 页面请求次数；**同一访客同一页 30 秒内的连续请求只算一次**（去抖：防预取、连点刷新、多标签）；
- **访客 uniq** = **按天去重的人次**：单页访客按 (天, 路径, 指纹) 去重；站点访客**按桶**按 (天, 桶, 指纹) 去重 —— 所以"先看首页、再点进作品页"的人**两边各算 1 个人次**，内页那次不会被吃掉；同一人不同天来各算一次（所以"全站访客"= 每日之和）；
- **只统计 HTML 页面**：静态资源、`/api/*`、`POST`、Range 请求、预取（`sec-purpose: prefetch`）、**分支预览部署**、**404/500 等非 200 响应**一律不计；
- **路径归一**：`/w-feng.html` 与 `/w-feng` 归到 `/w-feng`；
- **改口径只改一处**：`functions/_middleware.js` 里的 `CONTENT_PATH_RE` 正则（哪些算"内容页"）。

**真人怎么认**（`isSuspect()`）：只有拿到正向证据才算"疑机"——UA 命中黑名单（含 Googlebot、GPTBot、ClaudeBot、ChatGPT-User、Claude-User、Playwright、Puppeteer、Bytespider、Semrush…）／没有 UA／**没有 `Accept-Language`**／**来自机房 ASN 且没有 Sec-Fetch**。真人特征 = 有语言偏好，且（现代浏览器的 `Sec-Fetch-Mode: navigate`／`Sec-Fetch-Dest: document`，**或**老浏览器与**微信内置浏览器**的 `Accept-Encoding: gzip/br`）→ 这样**不会误伤**微信里打开、老 Safari 这些真实读者。机房 IP 不享受"语言+压缩"兜底（服务器抓取常伪装成 Chrome 但没有 Sec-Fetch）；只要带 `Sec-Fetch` 强信号，机房里的 VPN/云桌面真人仍照常算真人。`bot` 采用词尾匹配，CUBOT 等含 bot 字样的手机不会被误伤。

**编委自己不计入**：编委登录（或开了旧钥匙）后，前端会种 `zz_nostats=1` cookie，中间件见到直接跳过（JS 种的，所以"登录后第一个页面请求"仍可能算一次）。这个 cookie **12 小时过期、且只在当前域名生效**（`wuxu.org` / `www.wuxu.org` / `pages.dev` 各一份）：过期后第一页、换域名、换浏览器/无痕/清 cookie 的访问仍会被算进去。旧钥匙只存 `sessionStorage`，关浏览器即失效。

**隐私**：库里**不存原始 IP/UA**，只存 `sha256(日期|IP|UA|盐)` 的 24 位指纹（盐=当天，`STATS_SALT` 可选）→ 无法跨天追踪、无法反推 IP。

**额度**：每次约写 6 行。D1 免费版每天 10 万行写 → 约 **1.6 万次页面访问/天**。

**从哪天开始算**：**启用那天起**（2026-10-07），历史无法恢复；**"真假分辨自 Y 起"`（`stats_meta.split_since`）表示改版上线那天 —— **改版前的数字三个桶混在一起、拆不开**，看趋势请看改版之后。

### 有效阅读层（`reads` 表，2026-10-30 新增）

到达层只回答"页面被打开过"，回答不了"有没有人真的读"。这一层由页面里的 `beacon.js` 自报三个原始量，**判定在服务端**做（前端传来的 `engaged` 字段一律不看）。

**表**（`sql/stats.sql` 与 `functions/_middleware.js` 的 `SCHEMA_SQL` 必须逐字一致，`scripts/test-stats.js` 会比对）：

```sql
CREATE TABLE IF NOT EXISTS reads (
  day TEXT NOT NULL, vid TEXT NOT NULL, path TEXT NOT NULL,
  dwell_ms INTEGER NOT NULL DEFAULT 0, scrolled INTEGER NOT NULL DEFAULT 0,
  ref TEXT NOT NULL DEFAULT '', country TEXT, ts INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (day, vid, path));            -- 同一人·同一天·同一页最多 1 行
CREATE TABLE IF NOT EXISTS hit_reject (     -- 被拒原因计数（不许静默失败）
  day TEXT NOT NULL, reason TEXT NOT NULL, n INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (day, reason));
```

**门槛**（`functions/api/hit.js` 的 `engagedFrom`，改口径就改这三个常量）：

| 常量 | 值 | 含义 |
|---|---|---|
| `ENGAGED_MS` | `8000` | 可见停留 ≥ 8 秒（站着读完也算，不必滚动） |
| `SHORT_MS` | `4000` | 短页补充通道：≥ 4 秒 **且**（滚动过半 **或** 有过交互） |
| `SCROLL_MIN` | `50` | 滚动深度门槛（%） |

为什么短于 8 秒要多一个信号：本站多是短诗，一页**根本不可滚动** ⇒ 滚动比例恒等于 100%，若照"滚动≥50% 就算有效"的字面执行，"点开 0.5 秒就跑"也会被判成有效。

**接口契约**（`POST /api/hit`，body `{vid, path, dwell_ms, scrolled, interacted}`）：

| 响应 | 含义 |
|---|---|
| `200 {counted:true}` | 首次计入 |
| `200 {counted:false}` | 去重命中（同一人·同天·同页已记过） |
| `204` | 被过滤/不够门槛（**故意不返回 403**，不给爬虫"你被认出来了"的信号） |
| `429` | 同一来源 60 次/分钟 |

被拒原因写进 `hit_reject.reason`：`nostats`（编委自己）/`bot`（UA 黑名单或无 Accept-Language）/`rate`/`body`/`vid`（不是 UUID）/`path`/`notcontent`（入口页不参与）/`weak`（不够门槛）/`dup`/`error`。

**读者（vid）**：浏览器 `localStorage` 里的随机 UUID（键 `wuxu_vid`，有效期 365 天，每 30 天才续期一次）。同一设备同一浏览器 = 一个人；换设备/清缓存/无痕 = 新读者 ⇒ 「读者」也是**下界**。想让自己这台机器"重新做人"：控制台跑 `wuxuBeacon.forget()`。

**CSV 导出**（社刊年报）：`GET /api/stats?csv=1&days=90` 或 `&from=YYYY-MM-DD&to=YYYY-MM-DD`，表头 `日期,到达（内容页）,有效阅读,读者（去重）`，带 UTF-8 BOM（Excel 直接双击不乱码），仅编委可下。

**健康度**：`有效阅读 / 到达` 正常落在 **25%–45%**；接近 100% 说明有会跑 JS 又待得久的爬虫；低于 5% 先查 beacon 是否 404 / 被 CSP 拦，再查门槛。

**保留策略**：`reads` 是 `(day, vid, path)` 去重后的行（不是原始事件流，一年千行级），**不删**；只有 `hit_reject` 这种遥测按 90 天清（`pruneOldRejects()`，约每 500 次计数顺手跑一次，D1 没有 cron）。清明细等于把"累计阅读/读者人数/改版前上界"一起删掉，所以不做。

**看诊断（编委，不用写 SQL）**——在**你登录的那个域名**上打开（cookie 不跨域名）：

```
https://wuxu.org/api/stats?work=w-20240306-01&days=30&diagnose=1
```

`diagnose` 给四样：`siteTrend`（按天：内容页/入口页/疑机各多少）、`topPaths`（哪些页在被访问）、`pagesPerVisitor`（每个访客当天看了几页：真人常见 2+，扫描器几乎都 1）、`botRate`（疑机占比）。

**查库（D1 控制台）**：

```sql
-- 全站累计：内容页真人 / 入口页 / 疑机
SELECT SUM(views) AS 真人阅读, SUM(uniq) AS 真人访客,
       SUM(eviews) AS 仅入口阅读, SUM(euniq) AS 仅入口访客,
       SUM(sviews) AS 疑机阅读, SUM(suniq) AS 疑机访客,
       MIN(day) AS 起, MAX(day) AS 止 FROM site_daily;
-- 各页排行（先看内容页）
SELECT path, SUM(views) AS 真人阅读, SUM(uniq) AS 真人访客, SUM(eviews) AS 入口访问
  FROM page_daily GROUP BY path ORDER BY (SUM(views) + SUM(eviews)) DESC LIMIT 20;
-- 最近 14 天
SELECT day, views AS 真人阅读, uniq AS 真人访客, eviews AS 入口, sviews AS 疑机 FROM site_daily ORDER BY day DESC LIMIT 14;
-- 每个访客当天看了几页（真人通常 2+）
SELECT pages, COUNT(*) AS 访客数 FROM (
  SELECT visitor, COUNT(DISTINCT path) AS pages FROM page_visitors GROUP BY visitor
) GROUP BY pages ORDER BY pages;
```

> 想再加"最多人读的十篇"榜、或把数字改成公开显示，改 `functions/api/stats.js` 与 `auth.js` 的 `statsOn()` 即可；改完两种口径都记着跑一遍 `scripts/test-stats.js`（它会双向比对回溯 SQL 与 `CONTENT_PATH_RE`，也会比对公开接口与编委接口的数字是否一致）。**口径别乱动**，旧数据不可重算。

### 首页那行全站数字（**仅编委可见**）

首页 Hero 里、社名标语「同人结社 · 以诗会友，以文养心」与社名 `<h1>` 之间，有一行小字：

> 网站累计有效阅读 **N** · 读者 **M**

（**主数字只报这一种**；还没有 beacon 数据时显示 0，不再拿“到达/人次”顶替。完整说明见悬停 `title`。）

- 元素：`src/index.njk` 的 `#site-stats`（`hidden` 起手，构建期不留数字）
- 数据：由 `src/static/auth.js` 判定编委后去 `GET /api/stats?derived=1` 取 `reads.total`/`reads.readers`；没有有效阅读字段就整行隐藏，不退回旧口径
- 可见性：**只有编委**（账号 `role='编委'` 或旧共享钥匙）。读者与其它账号那里永远是空的
- 口径：**内容页**（作品 / 雅集篇目 / 期页 / 概念页 / 全文库）的**有效阅读**与**读者**；入口页不算。完整口径、有效/打开百分比、"上界"说明都写在元素的 `title` 里（那行太窄，塞不下括号注解）

**为什么没做成公开接口**（2026-10-15 的结论，别再翻回头）：一度实现过 `functions/api/site-stats.js`，把一个"作品累计阅读 N 次"放首页给所有人看，随后**删掉了**。原因是"访客/人次"这个词在公开场合站不住脚 ——

1. 指纹是 `sha256(当天|IP|UA|盐)`、按天更换 ⇒ **"总共多少人"这套设计算不出来**，只能给"人次"；
2. 改版（2026-10-14）之前的明细行**没有机器标记**，爬虫与真人混在一起、无法追溯分离 ⇒ 那个数只能当**上界**；
3. 公开页写「56 人次」不挂「≤」就是不诚实，挂了「≤」又像欲盖弥彰；而只公开"阅读次数"又会让人误以为是在说"多少人读过"。

既然内部看看就够了，就**收回编委可见**，不再对外暴露任何统计接口。

> 顺带一条 CSS 教训（线上真出过）：这个元素曾放在 `.motto` 里当 `<p>`，被 `.motto p{font-size:clamp(1.7rem,4vw,2.7rem);font-weight:700}` 盖成最大 43px 的粗体 —— 那行比社训还大。**父级如果有泛型标签选择器（`p`/`li`…），局部类选择器会被它压过去。** 现在放在 `.hero-copy` 下、用 `.hero-copy .site-stats` 兜底，`scripts/test-frontend.js` 里有两条断言守着（位置必须在标语与 `<h1>` 之间、不许放回 `.motto`）。

### 回溯重算（把改版前的历史也算成"内容页口径"）

新列只对**改版之后**的访问生效，所以光看 `site_daily` 会一直挂着改版前那份"混着围观"的累计。为了一次性看懂历史，接口在**编委诊断时**还会当场重算一份 `derived`（带 `&diagnose=1` 或 `&derived=1` 才跑 —— 作品页已不显示全站数字，就不必每次打开都跑一遍全表去重）：

| 字段 | 怎么来的 | 含义 |
|---|---|---|
| `derived.contentViews` | `page_daily` 里**内容页路径**的 `views` 之和 | 历史以来"有人读东西"的阅读次数（入口页那 300 多次不算）。**上界**——改版前的行没有机器标记 |
| `derived.contentViewsKnown` | 同上，但只算**没有历史残留行**的天 | **可信**阅读次数（改版后积累的那部分） |
| `derived.entryViews` | 非内容页路径的 `views + eviews` 之和 | 首页/作品库/社员/雅集/投稿的打开次数（**基本是爬虫与路过**） |
| `derived.contentUniq` | `page_visitors` 里"当天碰过 ≥1 个内容页"且 `bucket <> 's'` 的 `(天, 人)` 去重计数 | **真读者人次（上界）**——已排除疑机 |
| `derived.contentUniqKnown` | 同上，但只认 `bucket = 'c'`（改版后确定是真人） | **可信**真读者人次 |
| `derived.entryOnlyUniq` / `entryOnlyUniqKnown` | 全部 `(天,人)` − 上面那个 | 只逛了入口页的人次（上界 / 可信） |
| `derived.contentDaily` | 上面按天拆开，每天带 `clean` / `uniqKnown` / `viewsKnown` | **每天真正读过内容的人次** ← 看趋势用这个；`clean=false` 说明这天还夹着历史行 |
| `derived.legacyDayCount` | 还有几天留着 `bucket='u'` 的历史行 | `>0` ⇒ 界面**必须**把全站数字标成 `≤N`，不能当测量值 |
| `derived.note` | — | 提醒：历史行无法追溯补标，只能当上界 |

**口径修订（2026-10-14，修掉一个真 bug）**：`page_visitors` 原来**不分桶**，爬虫和真人写在同一批行里，于是上面这套回溯把"碰过作品页的 GPTBot / Bytespider / 扫描器"也算成了读者报出去。现在明细表每行带 `bucket`（`c` 内容页真人 / `e` 入口页真人 / `s` 疑机 / `u` 口径未知的历史行），回溯**一律排除 `s`**，并把 `c` 当可信值、`c`+`u` 当上界。

关键点：**历史行无法追溯补标**——加列之前的行一律是 `u`，所以改版前的数字永远是上界，不是测量值。界面上因此出现 `人次 ≤56` 这种写法，以及"其中 X 人次可确认为真人"的注脚。**这是刻意的：宁可难看，也不要报一个假的精确数。**

实现要点：分桶判据在 SQL 里写成 `path LIKE '/w-%' OR …`，与中间件的 `CONTENT_PATH_RE` 是**同一口径**——`scripts/test-stats.js` 会双向比对（任何一边改了前缀而另一边没跟着改，测试就会红）。`page_visitors(path)` 上另加了索引：主键是 `(day, path, visitor)`，`day` 在最前，不建索引的话回溯会全表扫。

### 快速自查清单（改完任何东西）

1. `npm run build` 无报错、Wrote 数量正常；
2. 涉及作品/刊期：`npm test` 会校验「期册 slug 必须有作品文件、不得重复、已入期 + 散作 == 全站篇目」——**名单一律从目录推导，没有登记表要同步**；
3. 涉及页面：本地预览翻一遍（尤其手机宽度）；
4. git 推送后等 1–2 分钟，用无痕窗口验证线上；
5. 提交信息按《提交规范.md》（Conventional Commits）。
